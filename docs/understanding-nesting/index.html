ネストの仕組みを理解する

Livewireコンポーネントは、他の多くのコンポーネントベースのフレームワークと同様に、入れ子（ネスト）構造を作れます。これにより、1つのコンポーネント内に複数のコンポーネントを配置してレンダリングすることができます。

ただし、Livewireのネストシステムは他のフレームワークとは異なる方法で構築されているため、理解しておくべきいくつかの特徴と制約があります。

まずは「ハイドレーション」の概念を理解しましょう

Synthesizerを使用する前に、Livewireのハイドレーションシステムを理解しておくと役立ちます。詳しくはハイドレーションのドキュメントをご覧ください。

すべてのコンポーネントは「島」として存在する​

Livewireでは、ページ上のすべてのコンポーネントは互いに独立しており、それぞれが独自に状態を管理し、他のコンポーネントとは独立して更新を行います。

例として、次のようなPostsコンポーネントと、その中にネストされたShowPostコンポーネントを見てみましょう：

<?php

namespace App\Livewire;

use Illuminate\Support\Facades\Auth;
use Livewire\Component;

class Posts extends Component
{
    public $postLimit = 2;

    public function render()
    {
        return view('livewire.posts', [
            'posts' => Auth::user()->posts()
                ->limit($this->postLimit)->get(),
        ]);
    }
}
<div>
    投稿上限: <input type="number" wire:model.live="postLimit">

    @foreach ($posts as $post)
        <livewire:show-post :$post :key="$post->id">
    @endforeach
</div>
<?php

namespace App\Livewire;

use Illuminate\Support\Facades\Auth;
use Livewire\Component;
use App\Models\Post;

class ShowPost extends Component
{
    public Post $post;

    public function render()
    {
        return view('livewire.show-post');
    }
}
<div>
    <h1>{{ $post->title }}</h1>

    <p>{{ $post->content }}</p>

    <button wire:click="$refresh">投稿をリフレッシュ</button>
</div>

初回ページロード時のコンポーネントツリーのHTMLは次のようになります：

<div wire:id="123" wire:snapshot="...">
    投稿上限: <input type="number" wire:model.live="postLimit">

    <div wire:id="456" wire:snapshot="...">
        <h1>最初の投稿</h1>

        <p>投稿コンテンツ</p>

        <button wire:click="$refresh">投稿をリフレッシュ</button>
    </div>

    <div wire:id="789" wire:snapshot="...">
        <h1>2番目の投稿</h1>

        <p>投稿コンテンツ</p>

        <button wire:click="$refresh">投稿をリフレッシュ</button>
    </div>
</div>

親コンポーネントは、自身のテンプレートとネストされたすべての子コンポーネントのテンプレートを含む完全なHTMLを出力します。

各コンポーネントは独立して機能するため、それぞれに独自のIDとスナップショット（wire:idやwire:snapshot属性）がHTMLに埋め込まれ、LivewireのJavaScriptコアがこれらを抽出して管理します。

では、異なるレベルのネスト構造において、Livewireがどのように更新を処理するのか、いくつかのシナリオで詳しく見ていきましょう。

子コンポーネントが更新される場合​

子コンポーネントshow-postの「投稿をリフレッシュ」ボタンをクリックした場合、サーバーに送信されるデータは次のようになります：

{
    memo: { name: 'show-post', id: '456' },

    state: { ... },
}

この要求に対して、サーバーから返されるHTMLはこのようになります：

<div wire:id="456">
    <h1>最初の投稿</h1>

    <p>投稿コンテンツ</p>

    <button wire:click="$refresh">投稿をリフレッシュ</button>
</div>

ここで重要なポイントは、子コンポーネントで更新が発生した場合、そのコンポーネントのデータだけがサーバーに送信され、その子コンポーネントだけが再レンダリングされるという点です。親や他のコンポーネントは一切影響を受けません。

次に、やや直感的ではない「親コンポーネントの更新」のケースについて見ていきましょう。

親コンポーネントが更新される場合​

まず、親コンポーネントPostsのBladeテンプレートを再確認してみましょう：

<div>
    投稿上限: <input type="number" wire:model.live="postLimit">

    @foreach ($posts as $post)
        <livewire:show-post :$post :key="$post->id">
    @endforeach
</div>

ユーザーが「投稿上限」の入力値を2から1に変更すると、親コンポーネントのみが更新されます。このとき、サーバーに送信されるリクエストのペイロードは次のようになります：

{
    updates: { postLimit: 1 },

    snapshot: {
        memo: { name: 'posts', id: '123' },

        state: { postLimit: 2, ... },
    },
}

このケースでは、親コンポーネントPostsのスナップショットのみがサーバーに送信されています。

ここで自然に生じる疑問は、「親コンポーネントが再レンダリングされるとき、子コンポーネントshow-postはどうなるのか？」ということでしょう。スナップショットが送信されていない子コンポーネントも再レンダリングされるのでしょうか？

答えは「再レンダリングされません」です。

LivewireはPostsコンポーネントをレンダリングする際、子コンポーネントを見つけると、その内容をレンダリングする代わりに単純なプレースホルダーを出力します。

更新後のPostsコンポーネントのHTMLは次のようになります：

<div wire:id="123">
    投稿上限: <input type="number" wire:model.live="postLimit">

    <div wire:id="456"></div>
</div>

投稿上限が「1」に変更されたため、子コンポーネントは1つだけ表示されています。しかし注目すべき点は、完全な子コンポーネントの内容ではなく、対応するwire:id属性を持った空の<div></div>だけが出力されていることです。

このHTMLがブラウザで受信されると、Livewireは親コンポーネントの古いDOM内容を新しいHTMLに_morph_（変形）しますが、このとき子コンポーネントのプレースホルダー要素は賢く処理され、その内容は保持されます。

このmorphing処理の結果、親Postsコンポーネントの最終的なDOM内容は次のようになります：

<div wire:id="123">
    投稿上限: <input type="number" wire:model.live="postLimit">

    <div wire:id="456">
        <h1>最初の投稿</h1>

        <p>投稿コンテンツ</p>

        <button wire:click="$refresh">投稿をリフレッシュ</button>
    </div>
</div>

パフォーマンスへの影響​

Livewireの「島」というアーキテクチャ構造は、アプリケーションにプラスとマイナス両方の影響をもたらします。

メリット​

この仕組みの最大の利点は、アプリケーション内の処理負荷の高い部分を独立したコンポーネントとして分離できることです。例えば、重いデータベースクエリを実行するコンポーネントを独立させることで、そのパフォーマンスへの影響を他の部分から隔離できます。これにより、一部のコンポーネントが低速であっても、アプリケーション全体のレスポンスには影響しません。

デメリット​

一方で大きなデメリットは、コンポーネント同士が完全に独立しているため、それらの間での連携や依存関係の実装が複雑になる点です。

たとえば、親コンポーネントPostsから子コンポーネントShowPostへプロパティを渡しても、それは「リアクティブ」に動作しません。各コンポーネントが「島」として存在するため、親コンポーネントで値が変更されても、子コンポーネントには自動的に反映されないのです。

解決策​

Livewireはこれらの課題に対応するため、次のような専用のAPIを提供しています：

  • リアクティブプロパティ
  • Modelableコンポーネント
  • $parentオブジェクト

Livewireのネスト機能の動作原理を理解することで、アプリケーション内でコンポーネントをどのように構成し連携させるべきかについて、より適切な判断ができるようになります。
